# 三维ESDF实时性问题说明：问题主要出在哪里

日期：2026-11-05。对象：`/home/czz/perception_eye_in_hand/nvblox_in_hand`。

本文只分析现有代码与已经完成的九轮三维ESDF输出测试，重点是问题所在。本轮没有启动仿真、没有运行新测试，也没有修改感知源码、参数或调度逻辑。

## 1. 核心问题

当前问题不是“ESDF话题完全发不出来”，而是：**点云发布接近30Hz，但其中有重复关联输入；跟随不同深度时间戳的输出只有约17～20Hz。恢复融合输入利用率后，ESDF输出更新组织没有同步解决。**

必须保留一个边界：约20Hz指的是点云中“关联新深度时间戳”的输出率，不是已经证明底层ESDF只计算了20Hz。两次显示输出之间可能有多次融合/ESDF操作，也可能合并多张输入。当前证据能确认输出链存在重复关联及未逐帧呈现，不能确认每个体素或每张输入的GPU完成时刻。

现有代码同时存在三个节拍：图像融合准入、周期ESDF更新、独立三维点云导出。三者没有按输入版本统一管理，因此调用次数、消息数与新输入关联数不能一一对应。

## 2. 已有实测反映出的问题

九轮中，融合门限30/33.4/40Hz各重复三次；所有组ESDF更新和显示门限均固定33.4Hz，同样开启三维诊断导出和RViz。输入为640×480、约30Hz，体素0.03m、范围3m，相机保持同一0.82m高位静止。

| 融合门限 | ESDF调用率 | 三维点云发布率 | 关联新深度输出率 | 相邻重复关联 | 输入年龄P50 / P95 |
| --- | ---: | ---: | ---: | ---: | --- |
| 30Hz | 32.87Hz | 29.47Hz | 17.07Hz | 42.0% | 59 / 106ms |
| 33.4Hz | 32.88Hz | 29.41Hz | 19.83Hz | 32.6% | 50 / 77ms |
| 40Hz | 32.91Hz | 29.26Hz | 19.77Hz | 32.4% | 50 / 77ms |

这张表说明：

- **只看topic hz会高估新输入的呈现频率。** 三组都约29Hz，但约三分之一至四成相邻消息关联相同深度时间戳。
- **提高融合门限有效，但收益没有完整传到输出端。** 30Hz门限下的低融合利用率改善后，新深度关联输出从17.07升至约19.8Hz，P95输入年龄从106ms降至77ms；并未得到30Hz的新深度关联输出。
- **33.4和40Hz融合组的ESDF实时性接近。** 19.83与19.77Hz的差异不能据此判断33.4更优；三轮波动范围重叠，当前主要剩余问题在更新/导出组织，而非继续提高融合门限。
- **约33Hz调用率不是约33Hz新地图。** 三组周期调用相近，而输入推进率不同，说明不能继续用调用计数作为主要实时性结论。

输入年龄由接收回调时最近的/clock减点云header计算，是近似数据年龄，不是屏幕端到端延迟或纯GPU耗时。关联输入推进按直接记录的整数纳秒header统计，不是通过点云内容哈希推断。

## 3. 问题一：原来的18Hz融合来自严格同频限流

本地官方 `shouldProcess()` 使用：

```text
当前图像时间戳 − 上一次融合图像时间戳 > 1 / 融合门限
```

门限30Hz对应严格大于33.333ms，而输入经常相隔33ms，于是正常输入被跳过，下一帧间隔累计至约66ms才通过；输入抖动使结果不是固定15Hz，而是此前重复测得约18Hz。

| 融合门限 | 严格最小间隔 | 问题/效果 |
| --- | ---: | --- |
| 30Hz | >33.333ms | 正常33ms帧可能被主动跳过 |
| 33.4Hz | >29.940ms | 大多数正常帧可通过，部分短间隔抖动仍可能被过滤 |
| 40Hz | >25ms | 给30Hz输入保留更多准入余量，不会创造40Hz图像 |

此前已经用参数余量恢复更多图像进入融合，当前默认仍为融合40Hz。**这一问题已部分解决，但它与后面ESDF输出重复、节拍不同步是两件事。**

源码：[官方门限判断](/home/czz/workspaces/isaac_ros-dev/src/isaac_ros_nvblox/nvblox_ros/src/lib/nvblox_node.cpp:564)。此前无三维导出负载的独立九轮实验测得融合门限30/33.4/40时，深度均值18.52/29.58/29.78Hz；这些是另一轮输入融合结果，不直接填入本轮ESDF实时性表。

## 4. 问题二：把ESDF调用次数当作输出版本

当前诊断节点的关键逻辑为：

```text
processEsdf:
    调用官方ESDF更新
    esdf_计数加一
    esdf_input_stamp_ = 当前最新融合深度时间戳

publishEsdfPoints:
    如果esdf_不同于上次导出版本，且显示间隔满足要求，则导出
```

代码只判断 `exported_version_ == esdf_` 是否相同，**没有要求本次深度输入时间戳比上次输出更大**。当ESDF周期调用了两次、期间没有新深度时，esdf_仍会增长，两次导出可携带相同header。

这在代码上足以解释“发布率接近30，但关联新输入更低”的现象。它不是底层距离场一定错误，而是诊断输出版本的定义不代表新输入或新地图内容。

源码：[processEsdf中的计数及时间戳赋值](/home/czz/perception_eye_in_hand/nvblox_in_hand/src/nvblox_in_hand/src/mapper_node.cpp:67)、[导出版本检查与header赋值](/home/czz/perception_eye_in_hand/nvblox_in_hand/src/nvblox_in_hand/src/mapper_node.cpp:75)。

### 机制示例，非本轮逐帧实测轨迹

| 事件 | 已融合的最新深度 | ESDF调用/导出 | 接收端看到什么 |
| --- | --- | --- | --- |
| 融合A后到更新周期 | A | 更新并发布 | header=A |
| 没有新深度，又到更新周期 | A | 调用计数仍增加，可再次发布 | header=A，重复关联 |
| 随后融合B、C，导出尚未到期 | C | 可能在周期中处理合并后的地图 | 尚无新的显示消息 |
| 再到导出时刻 | C | 发布当前地图 | header=C |

发布消息可以是A、A、C。不能由没单独看到B断言B未参与TSDF或ESDF，也不能把三条消息当三份新输入驱动的地图。

## 5. 问题三：融合、ESDF更新和显示是独立节拍

官方tick先处理输入队列，再检查周期ESDF任务；项目派生节点在官方tick返回后检查是否导出。整体为：

```text
约30Hz图像到达
    ↓ 图像时间戳门限决定是否融合
约10ms主tick处理图像队列
    ↓ ROS仿真时间决定是否到ESDF周期
processEsdf()
    ↓ steady wall-clock决定是否到导出周期
扫描/读回/组包/发布
    ↓ DDS与接收回调
三维点云到达
```

官方ESDF调度采用上次调用时间与当前时间之差，执行后把上次时间重置为当前now。30Hz门限常等到约40ms才满足；33.4Hz可以让名义约30ms的检查通过，提高调用率，但没有变成“每张新深度后立即进行一次更新并发布”的流水线。

显示使用独立steady_clock门限，并在导出开始时重置last_view_。即使两个配置数字都为33.4，也不代表融合、ESDF与导出相位相同；部分时刻会重复输出旧关联输入，部分中间输入状态可能未单独显示。

这不是说ROS仿真时间与steady_clock一定不能共用：仿真暂停时用不同时间源可以有合理用途。问题是当前没有清晰的输入版本、更新完成版本和导出版本之间的关联契约，周期设置不能代替版本管理。

源码：[官方输入处理及周期ESDF任务](/home/czz/workspaces/isaac_ros-dev/src/isaac_ros_nvblox/nvblox_ros/src/lib/nvblox_node.cpp:584)、[派生tick与导出位置](/home/czz/perception_eye_in_hand/nvblox_in_hand/src/nvblox_in_hand/src/mapper_node.cpp:45)。

目前重复header和代码条件已经确认；三个节拍各自对约20Hz推进率贡献多少，尚未逐任务跟踪，不能给出确切占比或把全部原因归到某一个定时器。

## 6. 问题四：诊断导出仍有同步与读回开销

原生CUDA导出器虽然不再构造固定空间查询格点，但仍会：

1. 获取全部已分配ESDF块索引，分批处理。
2. 扫描批内体素，筛选observed及有限距离，并压缩输出。
3. 将计数读回CPU并同步CUDA stream。
4. 将有效点读回CPU，再同步stream。
5. 组装PointCloud2并经DDS发布。

这些操作在 `publishEsdfPoints()` 中同步完成，位于派生tick里，所耗时间会占用当前处理链。默认observed导出不是只发送本周期发生变化的块；地图增长后扫描、读回和传输成本可能增大。

源码：[原生块扫描与筛选](/home/czz/perception_eye_in_hand/nvblox_in_hand/src/nvblox_in_hand/src/esdf_pointcloud_exporter.cu:47)、[计数/点集读回及同步](/home/czz/perception_eye_in_hand/nvblox_in_hand/src/nvblox_in_hand/src/esdf_pointcloud_exporter.cu:72)。

这证明导出不是零成本，但**没有证明它就是当前约20Hz输入推进的主要瓶颈**。本轮点数固定约24184、短窗稳定，尚无独立CUDA事件和导出关闭/开启严格对照来分摊GPU、CPU与传输耗时；不能直接宣称GPU算不动或大部分时间都在查询。

## 7. 问题五：现有统计还不足以证明完整端到端实时性

| 当前统计 | 已覆盖 | 尚未覆盖 |
| --- | --- | --- |
| 官方融合/ESDF计数 | 函数进入次数 | 每个输入对应的GPU完成时刻 |
| 点云消息率 | 接收端能收到多少消息 | 每条是否代表不同几何状态 |
| 点云header推进 | 输出是否关联不同最新深度 | 两次输出之间全部输入如何进入距离更新 |
| 输入年龄P50/P95 | 基于最近/clock的接收端新鲜度估计 | 精确曝光→GPU完成→发布→屏幕渲染延迟 |
| RViz FPS | 界面绘制频率 | ESDF计算/输入推进频率 |
| 短时三轮重复 | 当前静态场景下的波动 | 长期大地图、运动、自体残影和最坏情况 |

当前header只保存“最近融合深度时间戳”，不是完整的地图生成版本，也不是独立记录的ESDF任务完成时间。若想证明规划器何时拿到了包含某次观测的距离信息，仍需输入版本、TSDF更新、ESDF完成和可用数据版本之间的追踪。

特别不能把“约30.4ms调用间隔”写成“ESDF每次计算耗时30.4ms”；也不能把显示约29Hz写成所有体素都以29Hz重新计算。

## 8. 已确定与尚待确认的边界

| 判断 | 证据等级 |
| --- | --- |
| 原融合门限会过滤正常33ms输入 | 源码和多轮计数共同支持 |
| 三维输出存在相同关联时间戳的相邻消息 | 九轮直接记录header证实 |
| esdf_按调用增长而非按新输入增长 | 当前诊断源码直接确认 |
| 输出中不同输入的关联推进约17～20Hz | 本次接收端统计证实；不等于底层GPU完成率 |
| 三个节拍未按输入版本统一关联 | 当前调度/导出源码直接确认 |
| GPU扫描/读回同步产生额外成本 | 源码直接确认；主要瓶颈占比未确定 |
| 底层ESDF只更新20Hz、GPU性能不足 | 当前证据不足，不能下结论 |
| 77ms就是屏幕显示延迟 | 不成立；只是输入年龄估计的P95 |
| 去掉重复发布即可使新地图达到30Hz | 不成立；去重只能减少冗余，还需评估更新与导出的节拍关系 |

## 9. 后续解决方向：优先改关系，不是继续堆Hz

| 优先级 | 改善方向 | 对应问题 | 验收指标 |
| --- | --- | --- | --- |
| P0 | 建立新深度/TSDF变化块、ESDF完成、导出三种版本的关联 | 调用版本不等于数据版本 | 每条输出能追踪关联输入和实际完成状态 |
| P0 | 明确合并输入策略并协调更新/导出触发 | 相位不同，重复或未单独呈现中间状态 | 新深度关联输出率、输入年龄和尾部间隔，而非只看消息数 |
| P1 | 有新输入/变化才按策略导出，避免重复关联发布 | 冗余扫描、读回和DDS流量 | 重复关联比例降低，且输入年龄不恶化 |
| P1 | 使用输入、提交、GPU完成、导出/接收时间链定位延迟 | 当前无法分摊处理与队列开销 | 分段时延、可用地图年龄和P95/P99 |
| P2 | 根据实测瓶颈考虑变化块导出、缓存和减少同步 | 全块扫描/多次读回 | 相同输入、精度、范围和点数语义下，降低导出耗时 |
| P2 | 更大地图和移动相机长时测试 | 当前短静态窗口覆盖有限 | 长时吞吐、尾延迟、内存、残影与几何质量 |

本轮不实施这些方向。尤其不应只把计数名称改成“有效更新”或只删除重复消息，就宣称算法实际达到了30Hz；必须同时检查真实数据版本和数据年龄。

## 10. 可用于汇报的一段话

当前三维ESDF虽然能以约29Hz发布点云，但调用计数、发布次数和新输入关联并不一致。现有诊断代码以ESDF调用次数作为导出版本，即使没有新的深度输入也可能重复发布；融合、周期更新和显示又分别受独立时间门限控制，导致部分输出重复关联旧输入，部分中间融合状态未单独显示。九轮测试中，优化融合准入后，新深度关联输出约由17Hz提高到20Hz，P95输入年龄由约106ms降至77ms，但尚未实现30Hz的新深度关联输出。后续重点是按输入和地图变化建立更新/完成/导出的版本关系，并定位同步读回和队列延迟，而不是继续提高配置Hz或仅以topic hz判断实时性。
